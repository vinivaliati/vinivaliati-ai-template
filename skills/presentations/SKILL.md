# Presentations

A deck is an argument, not a container for content. The audience should get
the conclusion from the titles alone; the body of each slide is the evidence.
The brand stays the same everywhere; the occasion changes density, structure
and accent use.

**Read [brand/BRAND.md](brand/BRAND.md) fully before any slide.** It holds
the tokens, contrast rules, voice and the five occasion profiles. Never use a
color, font or size that is not there; if something is missing, ask.

## Templates

| Occasion | File | Default storyline |
|---|---|---|
| Status report | [assets/status-report.pptx](assets/status-report.pptx) | Summary, KPIs vs target, what changed and why, risks and blockers, asks and next steps |
| Kickoff | [assets/kickoff.pptx](assets/kickoff.pptx) | Goal, scope and out of scope, approach and phases, roles, risks, next steps with dates |
| Technical / portfolio (EN) | [assets/technical.pptx](assets/technical.pptx), [assets/technical.html](assets/technical.html) | Problem, architecture, key decisions, result, what I would do next |
| Pitch | [assets/pitch.pptx](assets/pitch.pptx) | Problem, insight, solution, proof (up to 2 big numbers), the ask |
| 1:1 and feedback | [assets/one-on-one.pptx](assets/one-on-one.pptx) | Check-in, wins, feedback with examples, growth, agreements |

The `.pptx` files are samples generated by
[scripts/build_templates.py](scripts/build_templates.py) from the slide
functions in [scripts/deck.py](scripts/deck.py). Build new decks with
`deck.py`, not by copying sample slides, so every slide follows the tokens.
After changing `BRAND.md` or `deck.py`, regenerate the samples:

```bash
uv run --with python-pptx==1.0.2 --with pyyaml==6.0.3 skills/presentations/scripts/build_templates.py
```

## Workflow

1. **Ask, in one round:** occasion, audience (who, what they know, what they
   decide), language (Portuguese for Brazilian clients and the team, English
   for portfolio and international), time slot, and the one thing the
   audience must remember or decide.
2. **Write the storyline** as a list of action titles, starting from the
   occasion's default storyline. Each title is a full-sentence conclusion.
   Show it and wait for approval before building anything.
3. **Collect the evidence** per slide: numbers with units and a comparison,
   the source of each chart. Missing numbers are asked for, never invented.
   Client data stays in the client deck; samples use fictional data.
4. **Build** with `deck.py`: one function call per slide, the occasion set on
   the deck so the profile applies (density, cover, accent use). Technical
   talks shown in a browser use `technical.html`.
5. **Check** (below), then render the deck to images and look at every slide
   before delivering.
6. **Deliver** the `.pptx` and a PDF export. Say which fonts must be
   installed or embedded (see `BRAND.md`, "Fonts in .pptx").

## Slide rules

- One message per slide. A second message means a second slide.
- Conclusion first: an executive summary up front for any audience that may
  leave early.
- At most one `amber` element per slide (two big numbers in a pitch).
- Charts: bars start at zero, the story bar in `amber`, the rest
  `bar-neutral`, values labeled, a source line under every chart.
- Tables: at most 6 rows and 5 columns on a slide; more goes to the appendix.
- Never below 11 pt. Content that does not fit goes to another slide.
- Client decks end with a concrete ask, an owner and a date.

## Check before delivering

- [ ] Reading only the titles tells the whole story.
- [ ] Every text color pair is "yes" in the `BRAND.md` contrast table.
- [ ] Only brand tokens: no loose hex values, fonts or sizes.
- [ ] Every chart has a source; every number has a unit and a comparison.
- [ ] No em dashes; no client names, logos or data outside a client deck.
- [ ] Rendered images reviewed: no overflow, overlap or cut text.

Render for review (LibreOffice):

```bash
soffice --headless --convert-to pdf deck.pptx
pdftoppm -png -r 50 deck.pdf slide
```

## The HTML version

`technical.html` is a single file with no build step: keyboard navigation
(arrows, space), progressive build only on architecture slides, a `?static`
mode that shows every step at once for screenshots and PDF, and no motion
when the viewer prefers reduced motion. Edit the slide sections in place;
styles come from CSS variables named after the `BRAND.md` tokens.
